# Contributing

Thanks for helping improve Zentauri UI. This repository contains the published React component package, the Next.js documentation site, demo apps, shared config packages, and a small backend.

## Setup

Use Node.js `>=18` and pnpm `9.0.0`.

```sh
corepack prepare pnpm@9.0.0 --activate
pnpm install
pnpm check-types
pnpm --filter @zentauri-ui/zentauri-components test
pnpm --filter component-library test
```

## Development Flow

1. Create a branch from `main`.
2. Keep changes scoped to the package or app you are touching.
3. Follow the existing component layering in `packages/components`: design-system constants, variants, types, implementation, entrypoint, tests, and docs.
4. Add or update tests for component behavior, keyboard support, accessibility semantics, CLI behavior, or generated output.
5. Run the relevant commands before opening a PR.

## Changesets

Run `pnpm changeset` when a PR changes the published package in a user-facing way:

- component, hook, chart, animation, or CLI behavior
- public prop or export changes
- design token changes
- peer dependency or package metadata changes
- package README or changelog changes that should ship to npm

Use:

- `patch` for fixes and small non-breaking corrections
- `minor` for new components, variants, hooks, charts, animations, or CLI capabilities
- `major` for breaking API, token, export, peer dependency, or CLI changes

Docs-site-only, CI-only, tests-only, and internal refactor PRs usually do not need a changeset.

## Pull Request Checklist

- Tests pass for the changed workspace.
- Type-checking passes for the changed workspace.
- Public package changes include a changeset.
- New components update docs, sidebar/search/SEO surfaces, tests, design-system exports, and build entries.
- Generated files such as `packages/components/cli/registry.json` are regenerated by their scripts, not edited by hand.

## Release Flow

Maintainers release from `main` through the GitHub Actions release workflow.
Because the npm package is published with provenance enabled, `pnpm release`
must run in the supported CI environment rather than from a local machine.

The release flow is:

1. Merge package changes with a changeset.
2. Let `.github/workflows/release.yml` open the Changesets version PR.
3. Merge the version PR after CI passes.
4. The same workflow publishes to npm with provenance using `NPM_TOKEN`.

The release workflow uses `CHANGESETS_TOKEN` when that secret is configured,
falling back to `GITHUB_TOKEN`. If GitHub Actions is not allowed to create pull
requests with the default token, add a fine-grained PAT as `CHANGESETS_TOKEN`
with repository contents and pull request write access, or enable the repository
Actions setting that allows GitHub Actions to create pull requests.

For local verification only, maintainers can run `pnpm version-packages` on a
throwaway branch to preview version and changelog output.
